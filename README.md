# bgp-attributes-executor

A dashboard that pushes and validates the **11 BGP path attributes** on a real
Cisco topology running in **EVE-NG** (Cisco 7206VXR / c7200 nodes), one scenario
at a time, with live logs and before/after `show ip bgp` diffs.

* **Lab:** EVE-NG on VMware Workstation, 8 x Cisco 7206VXR (c7200, Dynamips) —
  topology generated by `backend/scripts/build_lab.py`
* **Backend:** FastAPI + Netmiko + Jinja2, runs as a **Docker container on the EVE-NG VM**
* **Reachability:** each router's `Fa0/0` is in VRF `MGMT` on `192.168.99.0/24`,
  bridged out of EVE through `Cloud1` (`pnet1`). The container uses `network_mode: host`
  so it can reach both the EVE REST API (`127.0.0.1`) and the MGMT subnet.

```
frontend (browser)  ->  FastAPI :8000 (container on EVE VM)
                             |-- EVE-NG REST API  (topology, node state, console ports)
                             `-- Netmiko SSH -> 192.168.99.0/24 -> router MGMT VRF
```

## The 11 attributes → scenarios

| # | Scenario file | Attribute | What it demonstrates |
|---|---------------|-----------|----------------------|
| 01 | `01_weight` | WEIGHT | Local-only override on EDGE1, iBGP path wins |
| 02 | `02_local_pref` | LOCAL_PREF | Whole AS 65000 prefers ISP-A for a prefix |
| 03 | `03_as_path` | AS_PATH | Prepend on the ISP-B link steers inbound traffic |
| 04 | `04_origin` | ORIGIN | `igp` < `egp` < `incomplete` tie-break flip |
| 05 | `05_med` | MULTI_EXIT_DISC | `always-compare-med` across the two providers |
| 06 | `06_next_hop` | NEXT_HOP | Remove `next-hop-self`, watch the route go invalid |
| 07 | `07_atomic_aggregate` | ATOMIC_AGGREGATE | `aggregate-address summary-only` sets the flag |
| 08 | `08_aggregator` | AGGREGATOR / AS_SET | `as-set` adds AGGREGATOR, drops atomic-aggregate |
| 09 | `09_community` | COMMUNITY | Tag the enterprise aggregate toward ISP-A |
| 10 | `10_originator_id` | ORIGINATOR_ID | RR client sees the originator's router-id |
| 11 | `11_cluster_list` | CLUSTER_LIST | Cluster-id clash triggers RR loop prevention |

Every scenario has an **apply** and a **rollback** path and a set of verify
commands with regex assertions.

## Quick start

1. `python backend/scripts/build_lab.py` → `labs/bgp-attributes.unl`, import it in
   EVE-NG and start the nodes — see [`docs/eve-setup.md`](docs/eve-setup.md).
2. Bootstrap SSH + push the base configs — see [`docs/runbook.md`](docs/runbook.md).
3. On the EVE VM:

   ```bash
   git clone <this repo> /opt/bgp-attributes-executor
   cd /opt/bgp-attributes-executor
   cp .env.example .env      # edit EVE creds if not admin/eve
   docker compose up -d --build
   ```

4. Open `http://<eve-mgmt-ip>:8000/`.

## Repo layout

```
backend/
  app/            FastAPI application
  templates/      Jinja2 - one file per scenario (apply + {% if rollback %})
  scenarios/      YAML - targets, vars, verify assertions
  baseline/       full per-device IOS configs (known-good state)
  scripts/        build_lab.py, bootstrap.py, push_baseline.py, healthcheck.py
  inventory.yaml  devices, ASNs, mgmt IPs, router-ids, c7200 lab + link map
frontend/         single-page dashboard (vanilla JS + SSE)
docs/             topology, addressing, EVE setup, runbook
labs/             bgp-attributes.unl (generated by build_lab.py; committed)
```

## Monitoring: Kafka -> Prometheus -> Grafana

```
UI scenario run ─┐                                  ┌─> Prometheus :9090 ─> Grafana :3000
poller (20s)  ───┴─> Kafka :9094 ─> exporter :9108 ─┘
(EVE VM backend)      (Docker Desktop)
```

Topics: `bgp.neighbor.events` (up/down transitions, router reachability),
`bgp.neighbor.snapshots` (full state each poll), `bgp.config.changes` (every UI apply/rollback/reset).

1. **Windows (Docker Desktop):** set `KAFKA_ADVERTISED_HOST` in `.env` to the Windows IP the EVE VM can reach, allow inbound TCP 9094/3000/9090/8080 in Windows Firewall, then
   `docker compose -f docker-compose.monitoring.yml up -d --build`
2. **EVE VM:** set `BGP_KAFKA_BOOTSTRAP=<windows-ip>:9094` and `BGP_GRAFANA_URL=http://<windows-ip>:3000` in `.env`, then `docker compose up -d --build`.
3. Open the dashboard UI (`:8000`) - the *BGP session monitor* card shows live sessions and events. Grafana: `http://localhost:3000` (dashboard *BGP Network Monitor*, anonymous viewer). Kafka UI: `http://localhost:8080`.

Test: `shutdown` a neighbor on a router (or run a scenario) -> event appears in the UI feed, Kafka UI, and the Grafana state timeline; `BGPSessionDown` fires in Prometheus after 30s.
